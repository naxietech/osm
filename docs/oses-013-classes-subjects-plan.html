Module 2 · Planning

Building classes and subjects, end to end

Seven phases taking two reference-data screens from mock arrays to a live PostgreSQL backend and back into the browser — following the module pattern the auth work already established.

Settled before writing code

Four questions that changed the database shape. These are now fixed.

Group model
Each class owns its groups
Class 9's “Science” and Class 10's “Science” are separate rows. The global groups list goes away — it was already drifting from what the Class screen writes.
Tenancy
One shared list
No client_id anywhere. Every client teaches the same curriculum, so classes and subjects are national reference data.
“In use by” count
Left out for now
Students and exams have no tables yet. Returning a fake zero would invite someone to deactivate a class that is genuinely in use.
Scope
No curriculum
Three tables instead of four. Worth knowing: until curriculum exists, nothing connects a subject to a class.

Blocker found while planning

🚧
The web app cannot log into your API

Wiring any screen quietly contains “rebuild the web auth layer first”. The browser keeps a token in localStorage and sends it as a Bearer header. The API moved to HttpOnly cookies, which JavaScript is not allowed to read — and its login response carries no token at all.

  Web app expects API actually does
Where the token lives localStorage, readable by JS HttpOnly cookie — JS cannot read it
How it travels Authorization: Bearer … Cookie:, sent automatically
What login returns { user, token } { user } — no token
Cross-origin credentials not enabled required
Response shape uses the JSON as-is wrapped in { success, data, message, timestamp }
✅

The one piece of luck: CORS already allows localhost:5173 with credentials on, and all four auth routes work today. So Phase 0 is buildable and testable right now, against the backend already running.

The seven phases

Each phase runs the project's own gates before the next begins — not all saved for the end. The numbering is a real dependency order: Phase 0 gates everything after it.

00

Auth bridge

Size · Medium Risk · High Blocks 1–6

Rebuild the browser's half of authentication around cookies. Touches shared files, so it lands alone and lands first.

FileWhat changes
services/api-client.ts Add credentials: 'include'. Drop the localStorage token and Bearer header. Unwrap .data from the response envelope. On a 401, call /auth/refresh once and retry — if that fails, log out.
hooks/use-auth.tsx Remove token entirely. Signed-in becomes “/auth/me answered”. Call it once on startup — which is what isLoading finally means.
pages/auth/login.page.tsx Point at the real POST /auth/login.
apps/web/.env VITE_API_BASE_URL=http://localhost:3001/api/v1 — read by API_BASE_URL, not set anywhere today.

Standards: services and hooks only, no design-system files. use-auth.test.tsx and auth.service.test.ts both exist and both need rewriting.

Done when You log in through the browser, refresh the page and stay logged in, and keep working past the 15-minute token expiry without noticing.

Also in this phase: a small shared helper turning a Postgres duplicate-key error into a proper 409. Subject codes are unique, so this module hits the same bug the user-email endpoint has — it returns 500 instead of 409 when two requests race. Better fixed once, in one place, than twice.

03

The group tree endpoint

Size · Medium Risk · Medium Backend

PUT /classes/:id/groups — the only genuinely tricky piece, and the reason it gets its own phase.

  • One transaction. Either the whole tree saves or none of it does.
  • Rows arriving with an id get updated; rows without one get created.
  • Rows that vanished get deactivated, never deleted — so nothing pointing at them is ever orphaned. The mock deletes them, which is harmless today and breaks the day a student references a group.
  • Names unique inside their parent, enforced in the database as well as the browser.

Standards: this logic lives in the service, not the controller. Real unit tests — a rename, an add, a remove, a reorder, and a rejected duplicate.

Done when You build a three-level tree through Postman, edit it, and confirm the ids of untouched rows never change.
04

Wire subjects to the browser

Size · Medium Risk · Medium Frontend

Replace the subject half of academic.service.ts with real API calls behind React Query hooks.

🔗

The real work is a ripple, not the calls. ReferenceCrud is shared — both subjects.page.tsx and institute-categories.page.tsx use it. Making it async touches both, and institute categories has no backend. So ReferenceCrud has to carry a mock-backed page and an API-backed page side by side.

Standards: React Query for all server state — no useEffect fetch-and-set. Pages stay thin. Loading and error states reuse existing design-system pieces; no new one-off spinners.

Done when The Subjects screen creates a subject, you refresh the browser, and it is still there.
