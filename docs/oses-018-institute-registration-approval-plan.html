00

Decisions locked

Every question raised while planning, and what was decided. The rest of the document follows these answers. Two of them changed during the discussion and are marked.

1 · Does approving an institute also create its login?
Yes — one button. "Approve & Register" approves the institute and creates its user in the same action. Making the super admin approve first and then go to the Users screen is a double journey for no gain. The button lives on the detail page, not in the list table, behind a confirmation modal that says plainly what is about to happen.
2 · Where does the institute's password come from?
The institute sets it on the public form. With no email service there is no way to send a temporary password, so asking for it up front is the only flow that does not end in a phone call. It is hashed with argon2id the moment it arrives, stored in a separate table so it can never travel with an institute record, and destroyed as soon as the login exists or the application is rejected.
3 · What makes an institute unique?
The institute code, globally. One field decides whether an institute already exists. The uniqueness rule skips rejected and deleted rows, which is what lets a turned-away institute apply again using its real code.
4 · What about two institutes with the same name?
Allowed — names carry no constraint. Two "Government High School" in different cities is normal in Pakistan, and blocking it would reject real institutes. Instead a matching name + city raises a warning on the approval screen, never a block. Lists always show name + branch + city together so a human can tell them apart.
5 · Can a rejected institute apply again?
Yes. The rejected row stays, with its reason, as the record of who applied and was turned away. A fresh submission with the same code creates a new row. Blocking the code forever would mean one typo locks a real institute out permanently.
6 · How do we stop the public form being flooded?
Three cheap layers: a stricter rate limit on the public write route, a duplicate-code check that refuses a code already waiting for approval, and the approval queue itself as the final human gate. No captcha in phase 1 — it needs a third-party service, which brushes against the confidentiality rule.
7 · When does an applicant learn their code or email is taken?
At the step boundary — when they press Next past the step holding those two fields. This does reveal which codes and emails exist, which is normally avoided. It is accepted here because this is a form for institutions rather than individuals, the volume is roughly 150, it is rate-limited, and with no email service there is no other way to tell them. The check runs again at approval, because weeks can pass in between.
8 · What happens to file-type category questions?
Blocked, with a clear message. There is no file storage in the API yet. Accepting an upload and keeping only its filename would look like it worked and quietly lose the document — worse than refusing.
9 · One status field or two? changed
One: pending → approved → deactivated, with rejected as a dead end off pending. The old model carried onboardingStatus and isActive, which allowed nonsense states like "complete but inactive". The word is deactivate, not suspend, matching the rename already shipped in the users module.
10 · Who may edit an approved institute, and what?
Super admin and admin. Locked forever after approval: category, the question answers, the institute code, the numeric code. Everything else stays editable, including the contact email — contact people change jobs, and freezing the address means nobody can reach the institute. Editing it shows a notice: "Recommended — also change the login email for this institute." The two are deliberately separate; changing one never silently changes the other.
11 · Can an approved institute be deleted?
Only while nothing is attached — zero students, zero exams, zero users. That covers the real case: approved by mistake, or a duplicate. The row stays for the audit trail but the code is freed, so the institute can be registered again properly. Once anything is attached, deactivate is the only way out. A hard delete exists at no point.
12 · What does deactivating an institute switch off?
Its students, its evaluators — and any allocations those evaluators hold are released first, in that order, inside one transaction. An exam already running is not disturbed; the block is on future use. Results are never touched — a deactivated student's result stays valid and readable.
13 · Can the super admin register an institute directly?
Yes, and it lands as approved immediately. Making the approver approve their own entry is the same double journey rejected in decision 1. A registration_source column records public or admin, so you can always tell a self-registration from a staff entry.
14 · Does an institute have a parent? changed
No — the list stays flat in this branch. A board such as Lahore Board would naturally sit above its affiliated schools, and one nullable self-referencing column now would be far cheaper than re-parenting live data later. It was raised, considered and deliberately deferred. Recorded here so the decision is visible rather than forgotten. See Not in this branch.
15 · Multi-client tenancy?
Deferred. No client_id column. A speculative column that nobody fills is its own kind of debt — people read it as working isolation when it is doing nothing.
16 · Three fields the TRD never asks for
Dropped: registrationNo, instituteLevel and category (boys/girls/co-ed). They are left over from the older "School" model. One catch: the InstituteLevel enum stays in @oses/types because exam.types.ts uses it too — only the field leaves the institute.
01

What we are building

What the TRD asks for, what already exists, who will read this data, and the rules that must never break once a million students sit behind it.

What the TRD asks for Module 2

An open public link where an institute registers itself, and a Super Admin approval that turns the application into a real account. The fields: institute name with branch (e.g. "NSSOE, Shakargarh Campus"), institute code (government-provided, e.g. S01), category from Module 1, that category's dynamic questions with the institute's answers, type (Govt / Semi-govt / Private / Other), address, province, city, postal code, contact name, designation, contact email and contact number.

Why this table matters more than the table below it

An institute row is small — around twenty columns, and there will be roughly 150 of them. But it is the root of the entire data tree. Students hang off institutes, exams hang off students, marks hang off exams, results hang off marks. Every design choice here is inherited by a million rows that do not exist yet. Reference data is cheap to build and expensive to get wrong; root data is expensive both ways.

Rules that must always hold

  • An approved institute can never disappear. Results depend on it existing, years later. Deactivation hides it; nothing deletes it.
  • An answer must keep pointing at the question it answered. A stored answer references a permanent question id, and the database refuses to let that question be deleted while the answer exists.
  • The public form must create nothing but a queue entry. No login, no access, no permission — until a human presses approve.
  • A deactivated institute must not leave a working login behind. Switching off the institute while five staff accounts keep signing in is the failure mode to design against.
  • Two people approving at once must not create two logins. One approval, one transaction, one outcome.
  • No candidate data lives here. The contact details belong to institute staff, not to students. This module must never start holding student information.
02

Architecture

Four hard problems, and the same ports-and-adapters structure that auth and categories already proved.

Hard problem 1 — approval is four things that must be one thing

Pressing Approve & Register does four separate jobs:

1. flip status  pending → approved
2. assign the institute's permanent numeric_code
3. create the user from the stored email + password hash
4. destroy the stored credential

Any one of these failing must undo the other three.

Half-finishing produces exactly the states that are hardest to recover from: an approved institute nobody can log in to, or a user account belonging to an institute that is still pending. All four run in one database transaction. Either the institute is fully live, or nothing changed and the super admin sees an error and presses the button again.

Assigning the numeric code safely

The obvious way to pick the next number is SELECT MAX(numeric_code) + 1. It is also wrong. Two approvals happening at the same moment both read the same maximum and both write the same number.

Rejected MAX(numeric_code) + 1
Reads and writes are separate steps, so two concurrent approvals collide. The unique constraint catches it and one super admin sees a confusing error — for a number nobody typed.
Chosen A Postgres sequence
nextval() is atomic and never hands the same value to two callers. It also never reuses a number after a rollback — which is exactly what we want, because a reused number would make an old student registration number point at a different institute.

Hard problem 2 — a cascade with nothing to cascade to

Deactivating an institute must switch off its students and its evaluators, releasing those evaluators' allocations first. None of those tables exist yet. There is no students table, no evaluators table, no allocations table.

So the cascade cannot be implemented in this branch — but it can be defined. The categories module already showed the technique, and this module reuses it:

InstituteDependants  · a port owned by this module
   countStudents(instituteId)        → 0        (placeholder)
   countExams(instituteId)           → 0        (placeholder)
   releaseAllocations(instituteId)   → no-op    (placeholder)
   deactivateStudents(instituteId)   → no-op    (placeholder)
   deactivateEvaluators(instituteId) → no-op    (placeholder)

Real today, and genuinely used:
   countUsers(instituteId)           → real query against `users`
   deactivateUsers(instituteId)      → real — sets status + revokes sessions
Built now, switches on later

The interface, its call order and its tests ship in this branch as real code. When the students module lands, the protection turns on by filling in one method — not by trying to add cascade rules to a table that is already carrying a million rows. Designing the seam is the work; the implementation is the easy part that comes afterwards.

The one branch that is fully real today is the user half — because the users table exists. Deactivating an institute genuinely does deactivate its logins and revoke their sessions, reusing the machinery built for user deactivation.

Hard problem 3 — holding a password before a user exists

The institute chooses its password on the public form, but the user account is not created until approval, possibly weeks later. So a credential has to be stored against something that is not a user.

Rejected A column on institutes
It works, but it puts a password hash inside the row that every list, detail and mapper reads. One forgotten field in one mapper and a hash is in an API response. The safety depends on nobody ever making a mistake.
Chosen Its own table
institute_registration_credentials — one row per pending institute. The institute repository never selects it, so it cannot leak by accident. The row is deleted the moment the user is created, or the application is rejected.

This is the same reasoning that gave the categories module two controllers instead of one: make the unsafe thing structurally impossible rather than merely remembered.

Hard problem 4 — two front doors, one table

What the database itself enforces

Rules written only in application code are rules until somebody writes a script. These live in the schema.

RuleHowWhy it cannot be left to the service
One live institute per code Partial unique index on lower(institute_code) WHERE status <> 'rejected' AND deleted_at IS NULL A plain unique index would block a rejected institute from ever re-applying. A service-only check loses to two concurrent submissions.
Numeric codes are never shared UNIQUE on numeric_code, values from a sequence A duplicate here silently corrupts every student registration number built from it.
An answered question can never be deleted ON DELETE RESTRICT from institute_question_answers.question_id This is the constraint that makes Module 1's CategoryAnswerProbe real. Without it an admin editing a category could strand every answer to it.
One answer per question per institute UNIQUE (institute_id, question_id) Two rows for one question means the answer is ambiguous, and nothing would ever error.
Answers vanish with their institute ON DELETE CASCADE from institute_question_answers.institute_id Answers have no meaning without the institute that gave them.
A category in use cannot be deleted ON DELETE RESTRICT from institutes.category_id Deleting a category out from under 40 institutes is a data-loss bug, not a validation error. On Postgres 18 this surfaces as SQLSTATE 23001 — the shared pg-errors helper already handles it.
Only the four real statuses CHECK (status IN (…)), plus checks on institution_type, province, registration_source A typo'd status makes an institute invisible to every query that filters on it.

Converting users.institute_id the risky part of this branch

The column is text today with no foreign key, holding values like sch_001 that refer to nothing. It becomes uuid with a real constraint.

1. NULL out every existing value — none of them point at a real institute
2. alter the column type text → uuid
3. add the foreign key to institutes(id)
4. re-seed: create the demo institute, then point the seeded
   institute user at its real id
Step 1 discards data — deliberately

Every value in that column today is a mock id from the frontend prototype. There is no institute to preserve the link to, so keeping the strings would only carry the broken reference into a typed column. On a dev database this is harmless and the seed puts it back. If this branch ever meets a database with real institute users in it, step 1 must be replaced by a mapping step first. Say so in the PR description.

03·

Seed data

Small, insert-only, and safe to run twice.

  • One demo institute, approved, under the seeded School category — enough to give the seeded institute user somewhere real to point.
  • The seeded institute user is linked to it, which is what makes the new foreign key meaningful the moment the migration finishes.
  • Nothing is ever overwritten. Re-running the seed after an admin has edited the demo institute changes nothing — the same rule the categories seed already follows.
  • No permission changes. institutes.manage is already in the catalogue and already held only by Super Admin — verified against the running database.
Nothing to add to RBAC

This module introduces no new permission. Every route reuses institutes.manage, which the seed already grants to Super Admin alone. If a future role needs it, granting the permission is enough — no code change.

API surface

Two public routes with no login, eight admin routes behind the usual guard chain. Every response is wrapped by TransformInterceptor; controllers return plain data.

Public no login · tighter rate limit

RouteNotes
POST /public/institutes/check-availability Powers the step-boundary check. POST, not GET — an email in a query string ends up in server logs and browser history, which NFR-SEC-5 forbids. Answers only { codeAvailable, emailAvailable }, never a record.
POST /public/institutes The registration itself. Creates one pending row plus its answers and credential, in one transaction. Duplicate code → 409. A required file question in the chosen category → 400 with a plain explanation.
GET /public/institute-categories already exists Module 1 built it. The form draws itself from this.

Admin JwtAuthGuard → ActiveUserGuard → PermissionsGuard · institutes.manage

RouteNotes
GET /institutesPaginated, newest first. ?q= name/code search, ?status=, ?categoryId=. The total is narrowed by the same filters as the page, so "showing 10 of 3" cannot happen — the users module already sets this pattern.
GET /institutes/:idThe full record with its category and answers resolved, plus the duplicate-name warning when there is one.
POST /institutesSuper admin creates one directly → lands approved, numeric code assigned immediately.
PATCH /institutes/:idEdit. Sending a locked field (categoryId, answers, instituteCode, numericCode) on an approved institute → 400 naming the field, never a silent ignore.
POST /institutes/:id/approveApprove & Register. Body carries whether to create the login and the user's full name. One transaction, four steps. Email already taken → 409. Already approved → 409, not a second login.
POST /institutes/:id/rejectRequires a reason. Frees the code, destroys the stored credential.
PATCH /institutes/:id/statusDeactivate / reactivate. Deactivating runs the cascade in §02.
DELETE /institutes/:idSoft delete. Refused with 400 if anything is attached, and the message says what is attached and how many.
Error discipline

Every one of these throws a Nest HttpException and is shaped by HttpExceptionFilter. A unique-constraint violation becomes a 409, never a 500, through the shared pg-errors helper. The web app shows the server's own wording through apiErrorMessage() and never restates a rule in UI copy — that is how copy goes stale.

05

Scalability

The table is tiny. Everything that will point at it is not.

This table
Roughly 150 rows, growing by a handful a month. Every query on it is indexed and none of them will ever be slow. Paging the directory is about consistency with the rest of the API, not about performance.
What will point at it
1,000,000+ students, their exams, their scripts, their marks and their results — each carrying an institute reference, and each filtered by it constantly.

So the scalability work here is not about this table's own queries. It is about three things that a million child rows will inherit:

  • A uuid primary key that sorts well. Ids come from uuidv7(), which begins with a timestamp, so new rows land at the end of an index instead of scattering through it. Every child table's foreign key inherits that property.
  • A real foreign key on users.institute_id. Once institute scoping is enforced by the database rather than hoped for by the application, the query planner can use it — and the "own institute only" checks that every later module performs get an indexed path instead of a string comparison against nothing.
  • A numeric code that never changes and never repeats. Student registration numbers and roll-number blocks are built from it. If it were ever reused, a historical registration number would start pointing at a different institute — silently, and discovered years later in a results report.
The one thing deliberately left undone

A board with hundreds of affiliated schools has no way to express that relationship, because decision 14 deferred the parent column. If that arrives later it means re-parenting live institutes and revisiting every query that assumed a flat list. The decision is recorded, not forgotten.

06

Security

This module opens the first door in the system that anyone on the internet can push — and that door now accepts a password.

What the public endpoints can and cannot do

ConcernAnswer
Can a submission grant access?No. It writes one pending row. No login, no permission, no data, until a human approves.
Can the form be flooded?Rate-limited per IP, tighter than the global 100/min, plus a duplicate-code refusal and the queue as a human gate.
Can someone impersonate a real institute?They can apply as one. Approval is the defence, which is why the approval screen must show the govt code, contact name and phone number — everything needed to verify by phone.
Can the public response leak an admin field?The public controller returns a written allow-list, never an institute record. Widening it takes a deliberate edit in one file.
Does the availability check leak?Yes, by design and by decision. It confirms whether a code or email exists. Accepted for institutions at this volume behind a rate limit; recorded in decision 7 rather than left implicit.

How the password is handled

arrives  → validated (min 8 chars, same rule as create-user.dto.ts)
          → hashed with argon2id immediately — never written readable, never logged
          → stored in institute_registration_credentials (its own table)

approved → read once, becomes the user's password_hash
          → credential row deleted  (same transaction)

rejected → credential row deleted  nothing lingers

The separate table is the whole point: the institute repository never selects it, so no mapper, list endpoint or debug log can reach it by accident. Structural safety beats remembered safety.

Everything else

  • Every state change is audited — approve, reject, deactivate, reactivate, delete — with who did it, when, and the reason where there is one.
  • Deactivating an institute revokes its users' sessions, reusing the mechanism built for user deactivation. An open browser tab dies immediately rather than at token expiry.
  • No candidate PII passes through this module, now or ever. The contact details are institute staff.
  • Guards in the usual order — JwtAuthGuard → ActiveUserGuard → PermissionsGuard. Permission checks, never role checks, so a future custom role holding institutes.manage works without a code change.

They are the only ways back. A rejected institute can apply again from the start — that is why the code is freed. A deactivated institute can be switched back on — that is why nothing is deleted. Every other arrow goes one way.

Questions this plan expects

Why can't an approved institute be deleted?

Because a national examination board must be able to produce a result from four years ago, and that result is reachable only through the institute that issued it. Deleting the institute either destroys that chain or leaves rows pointing at nothing.

There is one narrow exception, and it is narrow on purpose: an institute with nothing attached at all can be soft-deleted, because there is no chain to break. That covers the real case — approved by mistake, or a duplicate — without opening the door.

Isn't storing a password before the user exists a bad idea?

It would be, stored badly. It is hashed with argon2id the moment it arrives, so there is nothing readable to steal, and it lives in its own table that the institute repository never touches — so it cannot leak through a mapper or a list endpoint.

The alternative is worse. With no email service, the only other option is the super admin inventing a temporary password and reading it down the phone, which means every approval ends in a phone call and a password that gets written on paper.

What if two super admins press Approve at the same second?

The first transaction wins. The second finds the status is no longer pending and answers 409 without creating anything. This matters more than it sounds: without the check, the second press would create a second user account for the same institute.

An institute typed its code wrong and was rejected. Now what?

They open the public link and register again with the right code. The rejection freed the old code, and the rejected row stays as the record of what happened.

With no email service there is no way to tell them they were rejected — the super admin phones them. That gap is why invite links are the first item in the next phase: a one-time link the super admin generates and sends over WhatsApp turns that phone call into something the institute can act on.

What happens to answers if the category's questions change later?

Nothing, and that is the point. Answers reference permanent question ids, never positions, so reordering or re-wording a question leaves every stored answer meaning what it meant.

The database refuses to delete an answered question outright — ON DELETE RESTRICT. Module 1 already anticipated this: it retires an answered question instead of deleting it, and the check that decides which is the CategoryAnswerProbe that finally becomes real in this branch.

Why tell a stranger that an email is already registered?

It is a genuine trade-off, and it was decided rather than overlooked. Normally you never confirm an account exists, and the usual way to avoid it is to accept the form and confirm by email — which we cannot do.

What tips it: these are institutions rather than individuals, there are about 150 of them, the route is rate-limited, and the alternative is an applicant learning days later, by phone, that their whole application was never viable. If that balance ever changes, the fix is one flag on the availability endpoint.

Why build a cascade for tables that don't exist?

Because the alternative is adding cascade rules to a live table with a million rows in it. Defining the interface now costs an afternoon and a set of tests; retrofitting it later means a migration, a backfill, and a period where the rule is half-enforced.

It also documents the decision in code rather than in a document nobody rereads. When the students module is built, the missing method is a compile-time obligation, not something someone has to remember.

Why does dropping three fields need its own phase?

Because it is not one task. registrationNo is institute-only and leaves cleanly. GenderCategory is institute-only and its enum can go too. InstituteLevel looks identical — but exam.types.ts and exam.service.ts use the enum, so only the field can leave.

A plan that had not checked would have said "drop three fields", and the build would have hit a type error in the exam module and someone would have made a call under pressure.
