OSES Classes — Build Plan Module 4

Classes, groups and subgroups, end to end

The Class → Group → Subgroup hierarchy taken from a mock array to live PostgreSQL and back into the browser. Two tables, one save, four phases — each gated before the next begins.

Decisions

Storage
Two tables
classes, plus one class_groups table holding both groups and subgroups. Not three tables, not JSON.
Saving
One tree, one call
The screen submits the whole tree. Known ids update, new rows insert, removed rows deactivate.
Group source
Per class
A class owns its groups outright. The shared groups catalogue stays mock-only and gets marked as such.
Removal
Deactivate only
No DELETE route anywhere. A million student rows will carry these ids.
Ordering
By ordinal
Kept as a real column — alphabetically “Class 10” sorts before “Class 9”, which is wrong.
Permission
levels.manage
Already in the catalogue. Not renamed to classes.manage — that would mean migrating live grants for a label.

Backend

Tables

classes
  id           uuid        primary key, generated
  name         citext      unique, 1–60 chars      ← 'Class 9'
  ordinal      smallint    not null, 1–99          ← progression order, not the name
  description  text        nullable, ≤ 200 chars
  is_active    boolean     not null default true
  created_by   uuid        → users.id
  updated_by   uuid        → users.id, nullable
  created_at   timestamptz not null default now()
  updated_at   timestamptz not null default now()

class_groups                                       ← groups AND subgroups
  id           uuid        primary key, generated
  class_id     uuid        not null → classes.id
  parent_id    uuid        nullable → class_groups.id
                             null = a group
                             set  = a subgroup of that group
  name         citext      not null, 1–60 chars
  is_active    boolean     not null default true
  created_at   timestamptz not null default now()
  updated_at   timestamptz not null default now()

Groups and subgroups share one table because they are the same thing at two depths — a name, an on/off switch, and a parent. A class with no groups (Class 1–8) simply has no rows here. No flag, no empty list to reason about.

What the database itself enforces

RuleHow
No two groups with the same name in one class unique (class_id, name) where parent_id is null
No two subgroups with the same name under one group unique (parent_id, name) where parent_id is not null
A subgroup cannot belong to a different class than its group unique (id, class_id) on class_groups, then foreign key (parent_id, class_id) references class_groups (id, class_id)
A group cannot be deleted while rows point at it No DELETE route exists. Withdrawal is is_active = false.
The one rule SQL cannot hold
A subgroup must not have subgroups of its own. A plain CHECK cannot look at another row, so the service enforces it: a parent_id must point at a row whose own parent_id is empty. There is only one write path — the tree endpoint — and it builds exactly two depths by construction. A unit test covers the rejection anyway.

Routes

RouteNotes
GET /classesOrdered by ordinal, with a group count per row. ?activeOnly= for pickers.
GET /classes/:idThe class with its full group/subgroup tree.
POST /classesName, ordinal, description. Duplicate name → 409 via the shared pg-errors helper.
PATCH /classes/:idName, ordinal, description.
PATCH /classes/:id/statusActivate / deactivate the class.
PUT /classes/:id/groupsReplace the whole tree. Id-preserving — see below.

All six carry JwtAuthGuard, ActiveUserGuard, PermissionsGuard and @RequirePermissions('levels.manage').

Nothing to add to RBAC
levels.manage is already in the permission catalogue (permissions.constants.ts) and only role_super_admin holds it.

The tree save

PUT /classes/:id/groups
{
  groups: [
    { id: 'a1…', name: 'Science',                 ← id known  → update
      subgroups: [
        { id: 'b2…', name: 'Biology' },           ← id known  → update
        {            name: 'Physics' }            ← no id     → insert
      ]},
    {              name: 'Arts', subgroups: [] }  ← no id     → insert
  ]
}

Any row in the database for this class that the payload does not mention
  → is_active = false.  Never deleted.

Ids sent back are preserved, so a student or exam already pointing at a group keeps pointing at it. The whole diff runs in one transaction — a half-applied tree is not a state anyone can observe. Ids that belong to a different class are rejected with a 400 rather than silently stolen.

The tree builder already exists and already works. It takes a value and emits a value, which is exactly the shape a live save needs — it only has to learn that saving takes time and can fail.

The form stays in its inline card, not a Modal. Subjects used a Modal because it is three fields. This form grows a row per group and a row per subgroup; on a phone a modal would fight it for height the moment a class has four groups. ConfirmDialog is still used before deactivating.

The mock arrays stay — and must say so
The exam form, checker form and student form still read levels and groups from academic.service.ts. Those arrays start drifting from the database the moment an admin adds a class. A comment naming which list is live and which is not is a required task in phase 4 — the same note subjects needs.

Phases

01Tables, entities, migration, seed

Both tables with their unique indexes and the composite foreign key, the two TypeORM entities, a reversible migration, and a seed of Class 9–12 with the groups and subgroups the mock carries today. Nothing wired yet.

Done when — pnpm db:migrate && pnpm db:seed creates and fills both tables, a second seed run changes nothing, db:migrate:revert cleanly drops them, and a hand-written INSERT of a subgroup under another class is refused by the database.
02Ports, repository, service, DTOs

Port interface and injection token, the TypeORM adapter, the service, and Zod DTOs with .strict() so unknown fields are rejected rather than silently dropped. The tree diff — update / insert / deactivate — lives here, in one transaction. Duplicate names translated to 409 through the shared pg-errors helper.

Done when — unit tests cover create, update, status, the duplicate-name path, and the tree diff in all four of its cases (kept, renamed, added, dropped), plus the two rejections: a foreign id, and a subgroup under a subgroup. npx jest green.
03Controller and routes

Six routes with their guards, permission decorator and Swagger annotations. The controller returns plain data; TransformInterceptor wraps it.

Done when — Postman creates a class, saves a tree, renames a group, drops one and sees it come back deactivated rather than gone; a non-Super-Admin gets 403; a duplicate class name gets 409, not 500.
04Rebuild the Classes screen

classes.service.ts through apiRequest, a useClasses() hook, and the page on React Query. Server messages shown through apiErrorMessage() — the 409 wording comes from the API, never restated in the UI. Every mutation invalidates the list, or a new class will not appear until the cache expires.

Done when — add a class in the browser, give it two groups and a subgroup, all of it appears without a refresh and survives one; reopening the form shows the tree exactly as saved; a duplicate name shows the server's own message; and no other screen's tests changed.

Student / exam foreign keysThose tables do not exist yet. class_groups.id is built to be their target the day they do.

InstitutionKindNothing sets it to anything but school. A later migration adds it when colleges or universities are actually configured.
Codes on groups and subgroupsThe type allows them; the form has never collected one and nothing reads them.
DeleteDeactivate is the withdrawal path, for the class and for every row in its tree.
Per-node CRUD routesSix extra routes to let the form save row by row, and a half-built tree becomes a real database state. One transactional save is both simpler and safer.
Reordering groups by dragGroups display in the order authored. Worth revisiting only if a class ever holds enough groups for the order to matter.
Sequencing
Same dependency as subjects: PR #16 (institute categories) is where pg-errors.ts comes from, and phase 2 needs it. Classes and subjects do not touch each other and can be built in either order — but both must land before curriculum, which is the module that connects them.
