OSES Subjects — Build Plan Module 3

Subjects, end to end

One reference-data screen taken from a mock array to a live PostgreSQL table and back into the browser. Four phases, each gated before the next begins.

Decisions

Tenancy
One shared list
No client_id. Every client teaches the same curriculum, so subjects are national reference data.
Removal
Deactivate only
No DELETE route. Nothing referencing a subject can be orphaned if the row never disappears.
Code uniqueness
Case-insensitive
citext, so PHY and phy cannot both exist. Enforced in the database, not only the form.
Ordering
By name
No sort_order column. Alphabetical is enough for a list this size.
Frontend scope
Subjects screen only
The six other screens reading subjects keep the mock array until their own modules land.
Page build
Written by hand
ReferenceCrud stays untouched, so the e-sheet screen carries no risk from this branch.

Backend

Table

subjects
  id          uuid        primary key, generated
  code        citext      unique, 1–20 chars     ← PHY and phy cannot coexist
  name        text        1–100 chars
  is_active   boolean     not null default true
  created_by  uuid        → users.id
  updated_by  uuid        → users.id, nullable
  created_at  timestamptz not null default now()
  updated_at  timestamptz not null default now()

Check constraints repeat the DTO's length rules, so bad data cannot arrive through a path that skips validation. No version column — a subject is three scalar fields and last-write-wins is the honest behaviour.

Routes

RouteNotes
GET /subjectsOrdered by name. ?activeOnly= for pickers.
GET /subjects/:idSingle fetch.
POST /subjectsDuplicate code → 409 via the shared pg-errors helper.
PATCH /subjects/:idName and code.
PATCH /subjects/:id/statusActivate / deactivate.

All five carry JwtAuthGuard, ActiveUserGuard, PermissionsGuard and @RequirePermissions('subjects.manage').

Nothing to add to RBAC
subjects.manage is already in the permission catalogue and only role_super_admin holds it — verified against the running database.

Phases

01Table, entity, migration, seed

The table with its check constraints, the TypeORM entity, a reversible migration, and the seed of the seven existing subjects. Nothing wired yet.

Done when — pnpm db:migrate && pnpm db:seed creates and fills the table, a second seed run changes nothing, and db:migrate:revert cleanly drops it.
02Ports, repository, service, DTOs

Port interface and injection token, the TypeORM adapter, the service, and Zod DTOs with .strict() so unknown fields are rejected rather than silently dropped. Duplicate codes translated to 409 through the shared pg-errors helper.

Done when — unit tests cover create, update, status and the duplicate-code path; npx jest green.
03Controller and routes

Five routes with their guards, permission decorator and Swagger annotations. The controller returns plain data; TransformInterceptor wraps it.

Done when — Postman lists, creates, edits and deactivates a subject; a non-Super-Admin gets 403; a duplicate code gets 409, not 500.
04Rebuild the Subjects screen

subjects.service.ts through apiRequest, a useSubjects() hook, and the page on React Query. Server messages shown through apiErrorMessage() — the 409 wording comes from the API, never restated in the UI. Every mutation invalidates the list, or a new row will not appear until the cache expires.

Done when — add a subject in the browser, it appears without a refresh, survives one, a duplicate code shows the server's own message, and the e-sheet templates screen still passes its tests untouched.
